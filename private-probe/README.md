# Private ByteBans compatibility probe

This directory contains test infrastructure only. Its plugin and Node client are not part of the releasable ByteBans JAR and must not be uploaded to Modrinth.

Build ByteBans with `mvn install`, then run `mvn -f private-probe/pom.xml package`. The test-only plugin depends on the real ByteBans plugin. On startup it inserts temporary probe punishments, dispatches Bukkit login, chat and movement events for synthetic non-staff and operator players, removes those punishments, and writes `plugins/ByteBansPrivateProbe/results.json`. These checks exercise the live Paper event bus and ByteBans listeners. They do **not** prove that an actual Minecraft client connected.

`matrix.json` pins exact Paper builds, binary SHA-256 hashes and Java runtimes for fifteen Minecraft versions from 1.21 through 26.3, each in online and offline mode. Four of these versions have experimental Paper builds and are labeled as such. `python private-probe/run_matrix.py --list` shows the 30 pinned targets without contacting the server. `python private-probe/run_matrix.py --target paper-1.21.4-online-synthetic` creates one selected isolated server from the frozen 1.1.0 JAR pair and pinned source revision, verifies the Paper and both plugin binary hashes, checks the plugin's startup log, reads the JSON result, saves a receipt under `private-probe/runs/`, and stops the server. Use `--jar` and `--source-revision` only for another exact candidate. Running without `--target` walks the whole matrix sequentially. The runner preserves every managed instance and world for later inspection. It uses ports 27200–27299, 4 GB RAM and four CPU cores, one server at a time.

`python private-probe/run_local_matrix.py --download-only` fills the pinned Paper cache from the publisher API and checks every SHA-256. `python private-probe/run_local_matrix.py --remaining` runs targets without passing receipts on the local Windows machine, one at a time, using the same frozen plugin/probe hashes. Each loopback-bound server uses game port 27240, 4 GB maximum RAM and four visible CPU cores, then stops; its world remains under `testing/bytebans/live/`. These local receipts are labeled `execution_host: local-windows-loopback`. They exercise synthetic Bukkit events, not a real player connection.

For a real protocol check, install the Node client with `npm ci --ignore-scripts` in `private-probe/client/`, then run `python private-probe/run_offline.py`. This creates a separate loopback-bound offline-mode Paper 1.21.4 target and opens an SSH loopback tunnel. Mineflayer joins as two non-operator test users. The script tests actual login, existing-session kick, shared-IP rejection, shared-IP chat mute and freeze/unfreeze movement. A console-only command in the separate testing helper measures the server's authoritative position; Mineflayer's predicted local position is recorded only as context. The script saves its result and stops the server. Use `--reuse <managed-id>` to retest a stopped instance only when its owner, mode, build, port and both JAR hashes match. It never opens the game port on the LAN or internet.

No Microsoft-authenticated bot is available for online-mode protocol login. The online-mode targets therefore use only synthetic event checks; they must be labeled as such. The offline TCP run supplies complementary real-client evidence, but does not by itself establish authenticated-session behavior. Failure or missing results do not imply compatibility.

For local real-client boundary checks, run `python private-probe/run_local_client.py <version>` for each of `1.21`, `1.21.4` and `1.21.11`. Each command creates a separate offline-mode loopback server on game port 27242 with RCON on 27243. Mineflayer checks actual Minecraft TCP login, IP punishment enforcement and authoritative freeze/unfreeze movement in a marked flat area. The release gate requires all three exact-JAR receipts. The separate Purpur matrix covers fourteen pinned releases in both direct modes; `run_local_purpur.py` and `run_local_purpur_client.py` add loader-specific boundary checks with real offline clients.

`admin_web_http_probe.py` is a separate private HTTP/SQLite smoke for an already-running test instance with `admin_web.enabled: true`. Run it only inside that container's network namespace on the test host, supplying the managed instance ID and frozen ByteBans SHA-512. It reads the private token file without printing the token, checks login, Host and CSRF rejection, then creates and undoes a note for a random unused UUID while verifying the database audit. Restore the test instance's original config and stop the server afterward. Never run this probe against a production database.

`python private-probe/run_local_admin_web.py` starts a separate loopback Paper 1.21.4 server with the admin page temporarily enabled on port 27247, runs the same HTTP/SQLite check against the new frozen JAR, stops the server and restores the disabled configuration. On Windows, the POSIX `0600` token-file mode assertion is inapplicable and explicitly recorded as unverified; the HTTP authentication, Host, CSRF and database audit assertions still run.

`python private-probe/run_local_mysql_network.py` checks the same frozen JAR on two loopback Paper 1.21.4 servers named alpha and beta. It creates a fresh MariaDB data directory under WSL `/tmp`, uses Unix-socket authentication for the test database's root account, and gives ByteBans a random test-only account; neither a production database nor a real Discord webhook is used. The servers occupy game/RCON ports 27310–27313, while MariaDB listens on loopback port 27314. Real offline clients check beta-scoped versus global IP bans and mutes, cross-server history/undo propagation, and behavior after beta restarts. The runner verifies that unaffected and newly unmuted chat appears in server logs, stores a machine-readable receipt under ignored `runs/`, then stops all services and retains the Paper worlds under `testing/bytebans/live/`. The exact-JAR release gate requires this receipt. Run `mvn -q -Dtest=DiscordWebhookNotifierTest test` for the separate localhost HTTP receiver test of Discord payload and rate-limit handling.

Run `python private-probe/summarize.py` to regenerate the local 30-target progress report for the frozen 1.1.0 JAR. It counts a target as passing only when its latest matching receipt includes all required event checks, matching deployed JAR and Paper hashes, clean startup diagnostics, and a stopped retained instance. Real-client and web-panel receipts remain separate evidence. Older `1.1.0-SNAPSHOT` results are preserved in [RESULTS-SNAPSHOT.md](RESULTS-SNAPSHOT.md) and never qualify the new JAR.

`python private-probe/make_paper_companion.py` creates the Paper-only 26.1.1 JAR. It verifies that all 2,136 JAR entries are identical to the primary frozen JAR except for one manifest marker. Modrinth rejects duplicate file hashes, so this companion can have its own Paper-only compatibility metadata without claiming nonexistent Purpur 26.1.1 support. Run `python private-probe/run_local_matrix.py --jar private-probe/frozen/release/ByteBans-1.1.0-paper-26.1.1.jar --port 27300 --target paper-26.1.1-offline-synthetic --target paper-26.1.1-online-synthetic` to retest the exact companion on separate local loopback servers. Both results are required and their worlds remain stopped and retained.

`python private-probe/release_gate.py --dry-run` is the ByteBans-specific release gate. It reads both exact frozen JAR hashes, the source revision and runtime-entry attestation, all thirty primary Paper targets, both companion Paper 26.1.1 targets, all 28 Purpur targets, the real-client, admin-web, and two-server MySQL receipts, and `release-changelog.md`. It writes `runs/release-dry-run.json` with every blocker. A missing, failed, stale, or mismatched mode blocks the release. The two proposed Modrinth versions form disjoint compatibility groups: the primary JAR lists Paper and Purpur for the fourteen shared versions, while the byte-distinct companion lists Paper 26.1.1. Bukkit and Spigot remain unverified for 1.1.0. The existing ByteBans 1.0.0 release is never edited or deleted.

Only after explicit owner instruction to publish, a passing dry-run, and that human review, run `python private-probe/release_gate.py --upload --user-approved-upload`. The uploader checks that the existing 1.0.0 version retains its pinned hash and compatibility metadata, creates or verifies the two distinct 1.1.0 beta versions, reads each back to verify its SHA-512/SHA-1, loaders, Minecraft versions, changelog and environment, then saves ignored `runs/publication.json`. An identical retry is idempotent; conflicting metadata stops the command. The default dry-run never opens an upload client. Run `python -m unittest discover -s private-probe -p test_release_gate.py -v` to test these gate behaviors without network writes.
